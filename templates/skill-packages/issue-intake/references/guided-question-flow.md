# 引导式提问流程

只问缺什么，够了就停。此 reference 负责"怎么问"；真缺口、duplicate、by-design、rejected、workaround 和证据阈值的判断属于 `pre-filing-judgment-card.md`。

## 提问原则

- Agent 先完成自己能做的所有动作（附件转文字、搜索历史、查模块知识、可行 live 验证），再问人。
- 按缺口提问，不要丢出一大张问卷。
- 够了就停，不要为了"看起来完整"继续问。

## 入口：先拿一句话

- 你报的是什么问题？先用一句话描述。
- 影响哪个功能或工作流？

连一句话都给不出 → 不进入起草，继续澄清。

## 判断是否存在真缺口

先问：你期望发生什么，实际发生了什么？这是已有能力坏了还是请求增加/增强能力？

目标：确认是否存在真实行为差异或真实需求缺口。只是"不会用""感觉不合理""看起来怪" → 不急于建 issue。

## 然后问定位上下文

- 哪些产品入口、执行入口、环境身份或版本事实会影响复现和路由？只问当前产品与 source 实际存在的维度。

如只提供了附件：请把其中影响判断的入口、环境身份和关键标识转写成文字。

## 预评估：先查模块知识

仅在 evidence 能映射到具体模块时，查阅与 claim 有直接证据关联的模块对应文件（`known-issues.md`、`decisions.md`、`rejected-features.md`）。判断：这是真缺口吗？是否已被已知设计边界解释？是否有已有 issue 覆盖？是否有可用 workaround？

如果已怀疑 duplicate/by-design/rejected，不停止在"查文档看像不像"，继续搜索真实 issue/comment 做实查。

**停止规则**：如能判定为 duplicate/by-design/rejected，在 intake 就停止。

## Bug/Regression 分支

按此顺序问：

1. **如何观察到的**：复现步骤？不能稳定复现的话怎么观察到的？
2. **期望 vs 实际**：应该发生什么？实际发生了什么？粘贴精确错误文本。
3. **影响**：谁受影响、在哪步被阻塞？持续/间歇/单次？何时开始、是回归吗？有 workaround 吗代价是什么？
4. **证据**：有哪些证据（截图、录屏、日志）？把关键证据转为文字。
5. **历史**：有没有与此匹配的已有记录？

**停止规则**：缺少能够定位 affected surface 的上下文、复现或观察路径、期望或实际，或附件中的关键事实尚未转为可检索文字时，不输出 ready-to-file。

## Feature/Enhancement 分支

按此顺序问：

1. **场景**：谁想要、在什么场景下？现在怎么做、摩擦在哪？
2. **期望能力**：系统应增加或改成什么？新能力还是增强？
3. **价值和优先级**：不做什么会被阻塞？哪个目标用户/工作流最受影响？有无时间窗口？现有 workaround 为什么不够？
4. **参考和证据**：有无参考产品、截图、原型、reporter 原话？转成文字。
5. **历史结论**：此方向之前被拒绝过吗？`rejected-features.md` 有高度相似需求吗？如果是重提，发生了什么变化？
6. **历史验证**：搜真实 issue/comment。此需求与历史重叠在哪、差异在哪？delta 是否改变了产品/验收边界？如历史是 wontfix，原因今天仍成立吗？

**停止规则**（以下任一缺失不输出 ready-to-file）：角色/场景不明确、当前痛点不明确、目标能力不明确、为什么重要不明确、无基本验收标准。

## 处理懒惰输入

常见输入："有问题看截图""客户想要这个功能""就是不对""看群聊"。

处理：
1. 不直接把原始文本接入 issue
2. 先补齐最少必要问题
3. 先查 duplicate/by-design/rejected 线索
4. 仍无法回答 → 输出 blocker 清单

恢复问题只围绕会改变 disposition 的缺口生成，例如 claim 是已有能力错误还是新能力请求、发生在哪个功能或工作流、期望与实际是什么、为什么重要。

## 停止条件

以下满足时停止提问进入输出：
- Intake disposition 已可判定
- 已有足够上下文描述位置、行为差异、影响
- 已可产出对应 outcome 的输出

**不满足时** → `blocked-needs-evidence`，不要为了"好歹建一个"继续。
