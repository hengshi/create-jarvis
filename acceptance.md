# Acceptance contract

## Journey and recovery

- One customer request creates or resumes one Construction Workspace.
- The method commit, authorized pointers, write policies, work cards, evidence and `Next` are durable and credential-free.
- Resume reverifies files, remote refs, writer liveness and runtime facts before continuing.
- Unknown writer ownership blocks a duplicate writer.

## Part 1 — Jarvis repo

- Provider/host/namespace/repo/visibility/default branch/publication mode are observed or explicitly unresolved.
- `templates/jarvis/` renders without unresolved tokens or foreign-customer facts.
- The published repo contains entry, modules/sources/cross-cutting/skills/references/tools and runtime governance scaffold.
- Starter workflows are `unverified`; the generated repo contains no construction work cards or create-jarvis method.

## Part 2 — Jarvis and Runtime Foundation

- Included modules have customer-language purpose, implementation and verification anchors.
- Sources and repo fleet point to real authorized systems; cross-cutting contains evidence-backed causal edges.
- `runtime-governance.md` identifies Runtime Environments, Agent HOME/discovery roots, authority, write/recovery boundaries.
- Jarvis repo owns stable bootstrap, quick/full sync, doctor, state/log and Scheduler Adapter, or records exact `pending-runtime-foundation` owner/action.
- Internal Runtime Jobs are Docker-unaware.
- Native Scheduler Adapter calls inner jobs directly; Docker adapter calls the jarvis-box release helper.
- No Jarvis mount, `JARVIS_HOME`, context/lock or jarvis-box Git lifecycle is introduced.

## Part 3 — Repository learning

- Every repo has an independent writer/card/branch/delivery ref.
- Episodes use real visible START where available; reconstructed START records sources and uncertainty and is generated outside Replay Agent context.
- Replay Agent cannot see final diff/outcome/root cause.
- Only a minimal delta that improves same-case behavior and passes adjacent regression is delivered.

## Reconciliation

- Jarvis and required repo-local remote refs resolve to exact delivered commits.
- One route from Jarvis entry through source/module to a real repo-local entry is behaviorally verified.
- Workflow content reflects real customer sources/roles/policies and is marked `verified` only with a revisitable case pointer.
- Incomplete unrelated coverage remains explicit.

## Part 4 — Docker and onboarding

- Public release checksum and OCI digest are verified; jarvis-box source is not required.
- Formal Agent HOME is persistent and does not bind the Host HOME.
- Jarvis Runtime Foundation bootstraps from zero inside the Docker Runtime Environment and survives removal of temporary bootstrap material.
- Sync/doctor and a real Runtime Agent invocation prove native Jarvis discovery.
- Host scheduler reaches the same Docker-unaware inner job through the release `runtime-job` helper; runtime and host failure logs remain separate.
- Generic jarvis-box health, Agent, Task/Run/state/workspace persistence, provider and optional connector probes pass.
- First supervised task completes or leaves exact evidence/blocker/`Next` in the onboarding card.
- No `jarvis-context.json`, `deployment-lock.json`, replacement manifest or readiness/onboarding state machine exists.

## Customer output

Report delivered repos/PRs/MRs, usable scope, Runtime Foundation status, formal runtime/operator entry, approvals, blockers, Construction Workspace path and next business result. Do not expose internal replay oracle or child-process mechanics unless needed for a concrete recovery.
