# Ponytail

> Based on `DietrichGebert/ponytail`. License: MIT.

Ponytail 缩短实现，不缩短调查。先理解任务、证据和 owner boundary，再选择能满足真实需求的最小改动。

## 使用时机

- bugfix：根因和影响面已有证据，准备进入 patch。
- feature delivery：scope 和验收条件已经明确，准备进入 repo 执行。
- repo-local 代码或文档修改：准备增加抽象、依赖、配置或新文件之前。

若 Jarvis 的质量门或 repo-local skill 更严格，遵循更严格的规则。

## 选择阶梯

在第一个真正满足需求的层级停止：

1. 这个改动是否真的需要存在？需求只是推测时不实现。
2. 当前代码库是否已有 helper、type、pattern、command 或文档结构？优先复用。
3. 标准库能否解决？
4. 原生平台能力能否解决？
5. 已安装依赖能否解决？
6. 一行清楚的改动能否正确解决？
7. 只有前面都不成立时，才写最少的新代码或文本。

## 第一性判断

增加 branch、gate、classifier、adapter、后台恢复或模型判断之前，回答：

1. 真实 trigger 是什么？
2. 哪个现有 proof signal 足以授权动作？
3. 该信号允许的最小动作是什么？
4. 缺少可靠信号时，哪些动作必须保持人工或显式触发？

优先使用现有 source-of-truth 字段、事件、状态转换或命令契约。不要从进程启动、轮询或偶然状态变化中推测人的意图。

## 规则

- 不增加任务未要求的抽象、接口、factory、plugin point、配置开关或未来脚手架。
- 一两行明显逻辑不为“整洁”而提取 helper；只有真实复用、稳定业务命名或复杂约束才值得提取。
- 能保持正确行为时，删除优于增加。
- 不为几行清楚代码或原生能力增加依赖。
- 文件数量保持最少并匹配 repo-local 风格。
- 不简化掉信任边界校验、数据丢失处理、安全、权限、可访问性和错误处理。
- 非平凡逻辑留下最小可运行验证；周边 repo policy 更严格时遵循 repo policy。

bugfix 的“最小”是最小 root-cause fix，不是在报告入口增加 guard 而让同类路径继续失败。修改共享函数前检查其调用者和相邻语义路径。
