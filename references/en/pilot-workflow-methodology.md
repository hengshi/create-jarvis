# Pilot Workflow Methodology

Use this when choosing and proving the first JARVIS loop.

## Principle

Start with one workflow that can produce evidence. Do not start by mapping the whole company.

A good first workflow has:
- a real user or owner;
- real artifacts already flowing through the company;
- a visible success signal;
- limited source/repo scope;
- enough recurrence to justify skill investment;
- a human who can judge whether the result is useful.

## Recommended Shape

1. Select one workflow.
2. Name the trigger and success signal.
3. Inventory only sources and repos needed for that workflow.
4. Build the minimum entry skill, workflow skill, source skill, and repo-local skill stubs.
5. Confirm truth-bearing fields.
6. Run shadow pilot on 3 to 5 real artifacts.
7. Record failures and no-skill-gap decisions.
8. Promote only durable learnings.

## Readiness Stages

- Installed: runtime can link the instance, but truth is not confirmed.
- First skill: entry skill exists and can route a narrow task.
- Pilot-ready: humans confirmed the first workflow, scope, owners, and target paths.
- Pilot-proven: at least one real START -> WORK -> END loop ran with evidence.
- Controlled ops: writeback and calibration are happening under owner review.
- Enterprise runtime: multiple workflows and repo/source skills are maintained by owners.

## Shadow Pilot Rules

In shadow mode, agents may:
- read and route;
- draft conclusions;
- propose writeback;
- produce handoff cards.

Agents may not silently:
- alter production source systems;
- rewrite repo-local truth;
- publish central JARVIS changes without approval;
- promote private examples to generic methodology.

## Evidence to Collect

For each pilot artifact, record:
- source artifact pointer;
- workflow stage reached;
- selected skills/references;
- success or failure;
- failure mode if any;
- writeback decision;
- next skill backlog change or `no_skill_gap`.
