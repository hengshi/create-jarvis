# Jarvis growth loop

This playbook covers decisions that cross construction parts or evolve an already usable Jarvis. It does not define a deployment lifecycle state machine.

## Construction loop

1. initialize and publish the Jarvis scaffold;
2. build evidence-backed Jarvis knowledge and Runtime Foundation;
3. learn repo-local execution from complete historical episodes;
4. reconcile delivered refs into one usable workflow route;
5. bootstrap that Jarvis into a formal Docker Agent HOME;
6. verify jarvis-box mechanics and run supervised real work;
7. write durable lessons to the single correct owner and repeat.

## Knowledge growth

Every candidate has `include / merge / defer / reject` disposition and evidence pointers. Modules represent stable customer capabilities, not repository or organization charts. Sources record access/routes, not content mirrors. Cross-cutting records causal next hops, not duplicated implementation truth.

Starter workflows remain `unverified` until real customer facts replace assumptions and a real or equivalent case proves their behavior. `verified` is evidence about the listed scope, not a global production phase.

## Runtime growth

The Jarvis repo evolves Runtime Foundation along this path:

```text
unresolved constitution
  → implemented bootstrap/sync/doctor/scheduler adapter
  → verified in native/Host Runtime Environment
  → bootstrapped and verified in formal Docker Agent HOME
  → maintained by quick/full sync and scheduled jobs
```

Jarvis updates flow from remote to cache to Agent discovery roots. jarvis-box releases flow independently as OCI image updates. Neither update path requires a joint manifest or lock.

## Learning growth

For each code repo:

```text
visible START → baseline replay → hidden outcome comparison
              → minimal repo-local delta → rerun → adjacent regression
```

Real issues are preferred. Inaccessible/missing originals trigger evidence-backed reconstruction by an isolated Agent. Commit messages and links remain discovery hints; they are never the learning result.

## Supervised use

After Part 4 probes pass, select a representative real task with the customer. Verify native Jarvis discovery, routing, repo-local execution, actual checks, writeback and operator observability. Gaps return to their owner:

- Jarvis route/knowledge → Jarvis repo;
- repository execution → repo-local skill;
- bootstrap/sync/scheduler → Runtime Foundation;
- Task/Run/runtime mechanics → jarvis-box;
- provider transport → connector/provider configuration.

Customer approval is a business decision, not a value written into a deployment state file.

## Continuing evolution

New evidence creates a normal Git change in the owning repo. After review/merge:

- Runtime Foundation sync materializes a new Jarvis revision;
- affected repo-local skills are updated through that repo's delivery policy;
- changed workflows are rerun against relevant cases;
- supervised work verifies high-risk behavior when necessary.

Do not mutate running container files as the source of truth, and do not couple Jarvis revision changes to jarvis-box image releases.
