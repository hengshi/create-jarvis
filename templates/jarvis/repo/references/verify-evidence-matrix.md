# 验证证据矩阵

## 核心规则

每条实质 claim 必须对应可直接检查的证据。仅凭静态推理不足以支撑运行时行为 claim 的验证。

## 按 Claim 类型选择证据

| Claim 类型 | 证据要求 | 说明 |
|-----------|---------|------|
| **身份 / 路由 claim** | 对该事实有 authority 的 source metadata | 从当前 source route 和 jarvis contract 查证目标身份及路由关系 |
| **静态存在 / 内容 claim** | 读取、解析或引用可达 | 用适合当前内容类型的读取或结构化解析方式直接确认目标的存在、结构和取值 |
| **运行时行为 claim** | 实际执行或实时观测 | 必须运行目标代码路径或观测实时系统状态，仅静态阅读不构成证据 |
| **行为变更 claim** | 原触发条件或已证明等效的入口 | 用原始触发方式重现；如不可用，需建立并证明入口的等效性后执行 |
| **验收 claim** | 逐条对应证据 | 每个验收条目单独核实，记录状态 |
| **非回归 claim** | 仓库或来源规约中的契约 + 风险选择检查 | 根据影响范围选择验证面和深度；不要求无条件全量回归 |
| **视觉 / 性能 / 迁移 / 安全 claim** | 仅当当前契约涉及对应的维度时才要求对应证据 | 不因“可能涉及”而自动扩展验证范围 |

## 证据记录

每份证据记录至少从语义上说明以下要素：

- **目标身份**：验证的是什么
- **执行动作**：执行了哪个命令或操作
- **实际结果**：观察到的输出或状态
- **来源**：证据从何处产生
- **局限性**：证据未覆盖的范围或已知盲区

记录形状服从当前 workflow/source contract；只保存与 target identity、结果、provenance 和局限性有关的字段。

## 证据状态

统一使用四种状态：

- `executed-pass`：执行验证，结果符合预期
- `executed-fail`：执行验证，结果不符合预期
- `observed-not-executed`：因环境、权限等原因未实际执行，但通过已有观测间接获得信息
- `blocked`：当前无法获取证据

自动化工具返回 PASS 仅代表其所涵盖契约通过，不等价于任意维度通过。每个证据的作用域由其实际执行的契约定义。
