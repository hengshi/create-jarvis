# Real customer-journey evaluation

End-to-end evaluation starts from the same interface a customer uses. Deterministic template tests do not replace Agent or Jarvis Box runtime evidence.

## Construction journey

1. Start from an ordinary authorized Host workspace without a create-jarvis checkout.
2. Send only the canonical one-sentence request from README.
3. Verify the Host Agent clones and pins the method locally, then asks for customer-provided sources instead of scanning HOME or history.
4. Verify it creates a recoverable Construction Workspace and can resume from its recorded `Next`.
5. Publish a customer Company Jarvis and independent repo-local deliveries from real evidence.
6. Reproduce reconciliation and one `construction-ready` workflow.
7. Verify deterministic scripts check structure, rendering and safety without claiming semantic or runtime completion.

## Formal runtime journey

Run the same construction output through both supported deployment choices over time; a release gate may select one mode per execution.

1. Ask the customer to choose Native or Docker.
2. Use the selected Jarvis Box public release contract without copying its Compose/env/internal-path implementation into create-jarvis.
3. Native: verify the existing installing OS user and native CLI authentication are used.
4. Docker: verify approved Host identities are imported narrowly into persistent runtime; Host HOME and SSH agent are not mounted.
5. Run the customer Runtime Foundation doctor and a real Agent discovery probe.
6. Complete one supervised chain:

```text
GitHub, GitLab or IM ingress
  → dispatcher
  → Task/Run
  → workspace when required
  → Runtime Agent
  → provider or IM writeback
  → terminal lifecycle
  → workspace and external-resource cleanup
```

7. Record actual mode, runtime owner/root, release version, Docker digest when applicable, identity capability evidence and optional connector boundary.
8. Advance only the selected workflow to `ready-for-shadow`; representative customer tasks and approval are required for `shadowing` and `active`.

Jarvis Box owns the real runtime happy paths and release evidence. create-jarvis owns the cross-boundary decision, generated work card/reference contract and consumption of released evidence. Neither repository implements a second copy of the other's lifecycle.
