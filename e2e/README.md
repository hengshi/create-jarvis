# End-to-end journeys

## Construction journey

1. Clone and pin create-jarvis from one customer request.
2. Explain requested source pointers and allow a pilot scope.
3. Create the Construction Workspace and verify recovery from an interrupted card.
4. Initialize, verify and publish a Jarvis repo from `templates/jarvis/`.
5. Build evidence-backed Jarvis knowledge and Runtime Foundation while independent repo cards learn real episodes.
6. For a missing original issue, verify isolated START reconstruction and outcome-blind replay.
7. Reconcile remote Jarvis/repo-local refs into one behaviorally verified route.
8. Confirm structure verifiers catch deterministic safety/path errors without claiming semantic completion.

## Formal Docker journey

1. Download/verify a public jarvis-box release and pin the OCI digest.
2. Prepare deployment/runtime/optional connector config and persistent volumes; do not prepare a Jarvis mount/context/lock.
3. Activate a separate formal identity in persistent Agent HOME.
4. Run the Jarvis-owned bootstrap inside the Docker Runtime Environment from an approved remote/ref.
5. Remove temporary bootstrap material; run stable sync/doctor and a real Agent discovery probe.
6. Install the Jarvis-owned host Scheduler Adapter and prove it calls the release `runtime-job` helper while the inner job remains Docker-unaware.
7. Verify generic jarvis-box toolchain, health, providers, Task/Run, Agent HOME/state/workspace persistence and optional connector.
8. Run one supervised route and record evidence/blocker/`Next` in the Construction Workspace.
9. Recreate the container and prove Agent HOME plus Jarvis discovery survive.
10. Update Jarvis through remote → cache → discovery roots without rebuilding the jarvis-box image; update jarvis-box image without changing the Jarvis ref.

jarvis-box owns image/Compose/persistence/control-plane tests. create-jarvis owns cross-boundary journey evals and consumes only public release behavior.
